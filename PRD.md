# PRD — Маркетплейс микрозаданий для генерации контента (Solana)

- **Версия:** 0.5 (добавлен игровой слой прогрессии — см. [`docs/GAME_DESIGN.md`](docs/GAME_DESIGN.md))
- **Дата:** 2026-09-14
- **Источник:** мастер-промпт «Контент-завод на Solana (SKR Task Marketplace)» v0.1 + ответы заказчика от 2026-09-14
- **Статус:** черновик. Разделы, помеченные ⚠️, не могут быть финализированы до закрытия вопросов из [`docs/OPEN_QUESTIONS.md`](docs/OPEN_QUESTIONS.md).

> **Название продукта: SixSec** ([ADR-0008](docs/adr/0008-product-name-sixsec.md)). Исходное имя из промпта — «SKR Task Marketplace» — перестало описывать суть: выплата идёт не в SKR ([ADR-0002](docs/adr/0002-payout-asset-own-game-assets.md)), а раздел 9 промпта запрещает связывать собственный актив с тикером SKR.

---

## 1. Проблема и цель

Студии нужны короткие видеоклипы (до 6 секунд) для продвижения трёх собственных крипто-игр. Нанимать продакшн дорого и медленно; краудсорсинг среди владельцев Seeker и крипто-энтузиастов Solana даёт объём и вариативность почти без фиксированных затрат.

**Цель продукта:** превратить генерацию промо-контента в игровой квест, где воркер получает внутриигровые ценности, а студия — поток одобренных клипов для рилсов и публикаций.

**Успех пилота измеряется не объёмом контента, а данными юнит-экономики:** стоимость одного одобренного клипа против измеримой отдачи (установки игр, покупки скинов, коннекты кошелька), привязанной к конкретному клипу через атрибуцию.

## 2. Пользователи

| Роль | Кто | Что делает |
|---|---|---|
| Заказчик | владелец студии | публикует бриф: промпт, референс, требуемая модель/настройки, язык, аспект, дедлайн, тиры награды |
| Воркер | владелец Seeker / крипто-энтузиаст Solana | берёт задание, генерирует клип своей моделью, отправляет результат |
| Модератор | член команды студии | рассматривает очередь после авто-префильтра, одобряет/отклоняет с указанием причины и выбором тира |
| Контент-оператор | член команды студии | забирает одобренные клипы в сборку рилсов, локализацию, публикацию |

## 3. Ключевой флоу

1. Заказчик создаёт задание с **тирами награды** (ADR-0004) и `max_claims` — сколько воркеров может взять задание параллельно (ADR-0003).
2. Воркер берёт задание (`claim`). Допускается до `max_claims` параллельных взятий — модель конкурса.
3. Воркер генерирует клип **сам**, своей моделью, за свой счёт, и отправляет сабмишен: хеш медиа + URI + **подписанное согласие на передачу прав**.
4. Авто-префильтр отсеивает явный брак (формат, длительность, NSFW, признаки копирайта).
5. Модератор рассматривает очередь, выбирает **тир** и одобряет либо отклоняет с причиной.
6. При одобрении воркер получает награду тира — игровые токены + NFT-предмет — **из пула призов** ([ADR-0006](docs/adr/0006-prize-pool-no-mint-authority.md)).
7. Контент-пайплайн забирает клип в рилсы, локализацию, публикацию.

**Пула касается отдельный операционный шаг:** студия пополняет пул вручную и вне программы, переводя активы из других проектов. Программа умеет только выдавать и не держит mint authority.

## 4. Ончейн-модель (отправная точка, с поправками принятых ADR)

> ⚠️ **Код ниже — проектная схема, а не скомпилированная программа.** Rust-тулчейна в текущей среде сборки нет (проверено), блок ни разу не собирался. Он фиксирует принятые решения в форме, близкой к коду; компиляция и тесты — задача Фазы 2.

```rust
#[account]
pub struct TaskAccount {
    pub task_id: u64,
    pub creator: Pubkey,
    pub brief_uri: String,          // промпт, референс, модель/настройки
    pub tier_count: u8,
    pub tiers: [RewardTier; MAX_TIERS],
    pub max_claims: u32,            // ADR-0003: вместо claimed_by
    pub claim_count: u32,
    pub reserved_amount: u64,       // ADR-0006: резерв в пуле по худшему случаю
    pub status: TaskStatus,         // Open | Filled | Approved | Rejected | Expired
    pub deadline: i64,
}

#[account]
pub struct ClaimAccount {           // ADR-0003: новый тип, PDA ["claim", task, worker]
    pub task: Pubkey,
    pub worker: Pubkey,
    pub claimed_at: i64,
    pub expires_at: i64,
    pub status: ClaimStatus,        // Active | Expired | Submitted
}

#[account]
pub struct SubmissionAccount {
    pub claim: Pubkey,              // ADR-0003: ссылка на claim, не напрямую на task
    pub task: Pubkey,
    pub worker: Pubkey,
    pub media_hash: [u8; 32],
    pub media_uri: String,
    pub consent_hash: [u8; 32],     // хеш подписанного согласия на передачу прав
    pub submitted_at: i64,
    pub moderation_status: ModStatus,   // Pending | AutoRejected | Approved | Rejected
    pub awarded_tier_id: Option<u8>,    // ADR-0004: тир выбирает модератор
    pub moderator: Option<Pubkey>,
    pub rejection_reason: Option<String>,
}

// Пул призов — PDA-токен-аккаунты, пополняются вручную вне программы (ADR-0006).
// Отдельного аккаунта-структуры не требует, но нужен PDA-учёт резервов:
#[account]
pub struct PoolState {
    pub admin: Pubkey,              // должен быть multisig, не single key
    pub total_reserved: u64,        // сумма резервов всех открытых заданий
    pub epoch: u64,
    pub withdrawn_this_epoch: u64,  // rate limit из раздела 3 промпта
    pub withdrawal_limit: u64,
}
```

Инструкции: `init_pool` · `init_profile` · `create_task` · `claim` · `submit` · `moderate(tier_id)` · `payout` · `refund_expired` · `withdraw_from_pool`.

Пополнение пула **отдельной инструкции не требует** — это обычный SPL-перевод на PDA пула, что соответствует «пополнять вручную» из ответа заказчика.

**Отличия от схемы промпта и почему:**

| Изменение | Причина |
|---|---|
| `claimed_by: Option<Pubkey>` → `max_claims` + `ClaimAccount` | ADR-0003: исходное поле жёстко фиксировало эксклюзив на одного воркера |
| `reward_amount`/`reward_mint` → `tiers: [RewardTier; N]` | ADR-0004: тиры, выбор при одобрении |
| статус `Claimed` убран из `TaskStatus` | при M параллельных воркерах задание остаётся `Open` |
| добавлен `refund_expired` | в промпте статус `Expired` есть, а инструкции возврата нет — средства зависали бы навсегда |
| добавлен `consent_hash` | раздел 9 промпта требует согласие на передачу прав во флоу сабмишена; хеш делает его ончейн-доказуемым |
| `EscrowVault` на задание → единый `PrizePool` + `PoolState` | ADR-0006: заказчик пополняет общий пул вручную, программа только выдаёт |
| добавлены `reserved_amount` / `withdraw_from_pool` | ADR-0006: при общем пуле и тирах размер выплаты неизвестен до модерации, нужен резерв по худшему случаю |
| программа **не** держит mint authority | ADR-0006/0007: активы наград внешние и уже существуют |

## 4.1 Игровой слой прогрессии

Полный дизайн — [`docs/GAME_DESIGN.md`](docs/GAME_DESIGN.md). Ключевые решения:

- **[ADR-0012](docs/adr/0012-sim-layer-cannot-pay-real-value.md):** симуляционный слой (тренировочные миссии, опыт, софт-валюта, апгрейды агентства) не имеет **ни одного кодового пути** к пулу призов. Инвариант держится не дисциплиной, а отсутствием пути: `payout` требует `SubmissionAccount` со статусом `Approved`, а симуляционные миссии таких аккаунтов не создают.
- **[ADR-0011](docs/adr/0011-progression-split-onchain-offchain.md):** on-chain только `WorkerProfile.trust_score` и порог `LIGHT_MODERATION_THRESHOLD = 700` — это граница безопасности, за ней стоит `payout`. Опыт, дерево навыков, гильдии, лидерборды — off-chain, чтобы баланс игры можно было править без деплоя.
- **PvP-питчи не требуют нового кода** — это `max_claims = 2` из [ADR-0003](docs/adr/0003-claim-model-parallel-submissions.md).
- **Асимметрия trust score:** +15 за одобрение, −25 за отклонение, −40 за авто-отклон. Один авто-отклон отбивается тремя одобрениями — защита от фарма объёмом.

```rust
#[account]
pub struct WorkerProfile {           // PDA ["profile", worker]
    pub worker: Pubkey,
    pub trust_score: u16,            // 0..=1000, меняется только в `moderate`
    pub approved_count: u32,
    pub rejected_count: u32,
    pub auto_rejected_count: u32,
    pub last_updated: i64,
}
```

**Награды — гибрид ([ADR-0015](docs/adr/0015-hybrid-reward-skr-rank-bonus.md), Q23 закрыт 2026-09-15).** Базовая награда — **собственные NFT-предметы и внутриигровые токены** студии ([ADR-0002](docs/adr/0002-payout-asset-own-game-assets.md)): их нельзя эмитировать как SKR, и они не переводят расчёты в денежную плоскость. Поверх базовой награды верхние ранги получают **бонус в SKR**: 100 SKR с trust score 850, 250 SKR с 950. Бонус считается от ранга, а не от сложности задания, поэтому не входит в тиры брифа и выплачивается отдельной инструкцией `payout_rank_bonus`.

⚠️ **Гибрид вводит реальный денежный бюджет:** SKR нельзя заминтить, его покупают на рынке. Лимит объёма выплат не определён (Q26), номинал в SKR означает плавающую стоимость в USD (Q27), а mint SKR не проверен ончейн. До первой реальной выплаты нужно письменное юридическое заключение (раздел 9).

Резервы под задания учитываются **отдельно по каждому минту** (`MintReserve`): при двух активах в пуле суммирование их резервов в одно число было бы бессмысленной арифметикой.

## 5. Оффчейн-компоненты

- **Backend:** Node.js/TypeScript, Postgres, BullMQ/Redis. CMS брифов, приём сабмишенов, очередь модерации, дашборд, нотификации.
- **Хранилище медиа:** Arweave (Turbo) как основной — совпадает с конвенцией ассетов dApp Store; IPFS + S3-зеркало как отказоустойчивость. ⚠️ Q9: кто платит за загрузку.
- **Авто-префильтр:** формат, длительность, NSFW, эвристика копирайта. ⚠️ Q10: конкретный стек и бюджет на инференс.
- **Клиент:** мобайл-центричный, Solana Mobile Wallet Adapter (Seed Vault на Seeker). ⚠️ Q8: PWA+Capacitor vs React Native/Expo.
- **Контент-пайплайн:** сборка рилсов, локализация (субтитры/дубляж), на MVP ручной экспорт под площадки. ⚠️ Q14: языки и площадки.

## 7. Анти-фрод

Опциональный стейк, rate limit на кошелёк за эпоху, репутационный скор, привязка к верифицированному устройству Seeker. ⚠️ Q12: требуется ли Seeker/Seed Vault для участия — сильно влияет на размер воронки.

**Специфично для модели конкурса (ADR-0003):** при `max_claims = N` отклонённые воркеры работали впустую. До взятия задания UX обязан явно это показывать, иначе репутация площадки падает.

## 8. Юнит-экономика ⚠️

Раздел 8 промпта предписывал считать «стоимость награды в USD-эквиваленте на момент выплаты». После ADR-0002 знаменатель меняется: выплата идёт собственными токенами и NFT, у которых может не быть рыночной цены.

Предлагаемая переформулировка (требует подтверждения):
- **затраты** = себестоимость минта + упущенная ценность выданной внутриигровой ценности + операционные расходы (хранилище, инференс префильтра, труд модератора);
- **отдача** = установки игр, покупки скинов, коннекты кошелька, привязанные к клипу через UTM-атрибуцию.

**Q19 закрыт по существу:** заказчик подтвердил, что воркер может продать награду на рынке внутри игр. Значит у награды есть наблюдаемая цена и знаменатель возвращается.

⚠️ Остаётся уточнить, **в чём деноминирована** эта внутриигровая цена (SOL / внутриигровая валюта / стейблкоин) — без этого себестоимость клипа посчитать нечем.

## 9. Юридическое ⚠️ НЕ ЗАКРЫТО

Требование мастер-промпта (раздел 9, D6): консультация юриста **до** первых реальных выплат. Ответ заказчика «это вознаграждение игровое считается как часть игры миссия» — квалификация заказчика, не юридическое заключение; подробности в `docs/OPEN_QUESTIONS.md` F.4.

Чек-лист, который остаётся в силе:
- [ ] квалификация выплаты воркеру (труд / приз / баунти / внутриигровая награда)
- [ ] объём передаваемых прав на контент и текст согласия (Q13)
- [ ] налоговые последствия трансграничных выплат
- [ ] проверка, что референсы и промпты не нарушают чужие IP/товарные знаки
- [ ] AML/KYC-пороги (Q12)
- [ ] гайдлайны модератора соответствуют политике dApp Store
- [ ] тикер собственного токена не `SKR` и не коллидирует в реестрах (Q18)
