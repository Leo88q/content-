# ADR-0014: Интеграционные тесты на LiteSVM заблокированы, путь — Surfpool

- **Статус:** принято (фиксация известного ограничения, а не обход)
- **Дата:** 2026-09-15
- **Уточняет:** [ADR-0013](0013-test-toolchain-solana-3-1-10.md)

## Контекст

Интеграционные тесты `programs/sixsec/tests/test_init_pool.rs` компилируются, но падают на загрузке программы в виртуальную машину:

```
panicked at tests/test_init_pool.rs:41:10:
программа должна грузиться в LiteSVM: Instruction(InvalidAccountData)
```

Пять прогонов CI (34908988418, 34909606020, 34910476210, 34911205914, 34911925781) дали одну и ту же ошибку. Что было проверено, а не предположено:

1. `litesvm 0.10.0` тянет `solana-bpf-loader-program = "3.1.0"` и `agave-* = "3.1.0"` — его загрузчик из линии Solana 3.x.
2. Взять более свежий LiteSVM нельзя: 0.14 тянет `agave-* 4.1.1`, 0.16 — `4.2.1`, то есть `solana-* 4.x`. `anchor-lang 1.2.0` пинит `solana-* ^3`, поэтому `Pubkey` в тестовом крейте оказывается двух несовместимых версий.
3. Именно поэтому собственный шаблон Anchor 1.2.0 (`cli/src/template.rs`, `TestTemplate::Litesvm`) пинит `litesvm = "0.10.0"` — при рекомендованном для той же версии CLI 4.1.2. Рассогласование существует в самом Anchor.
4. Перевод `Anchor.toml` на `solana_version = "3.1.10"` не помог. Важно: этот пин перекрывает версию CLI из окружения, так что менять её только в CI бесполезно — проверено на run 34910476210.
5. Принудительная пересборка (`rm -rf target/deploy target/sbf-build`) тоже не изменила результат.

## Решение

Тесты **запаркованы** через `#[ignore]` с указанием причины. Они остаются в репозитории, компилируются и будут запущены, как только появится совместимая виртуальная машина.

CI при этом остаётся зелёным осмысленно: сводка публикует фактическую строку `test result:`, и для интеграционных тестов она читается как `0 passed; 0 failed; 3 ignored`. Скрыть провал за «успехом» не получится — ровно та ошибка, которая уже была допущена в run 34906081661.

## Дальше

Перевод на **Surfpool**. Это не компромисс, а возврат к мастер-промпту: раздел 4 предписывает «юнит — LiteSVM/Mollusk; **интеграционные — Surfpool**». Использование LiteSVM для интеграционных тестов было моим отступлением от этой схемы, и именно оно упёрлось в ограничение загрузчика.

До перевода интеграционное покрытие полного цикла `create_task → claim → submit → moderate → payout` **отсутствует**. Это осознанный и зафиксированный пробел, а не закрытая задача.

## Что покрыто сейчас

29 юнит-тестов, которые реально проходят в CI:
- логика пула: резерв по самому дорогому тиру, игнорирование неактивных тиров, переполнение `u64` как ошибка, границы `available_balance`, отказ вывода при затрагивании резервов и при превышении лимита эпохи;
- динамика trust score: насыщение без wrap, стоимость авто-отклон, падение рейтинга при чередовании брак/годнота, граница порога 700, недостижимость облегчённого тира из нуля за 46 одобрений, обратимость тира.

Не покрыто: любая инструкция целиком, PDA-деривации, авторизация `moderate` на реальном выполнении, CPI в token program.
