# ADR-0006: Награда выдаётся из пула призов; программа не держит mint authority

- **Статус:** принято
- **Дата:** 2026-09-14
- **Решает:** Q17

## Контекст

После ADR-0002 (выплата собственными игровыми активами) эскроу из мастер-промпта потерял исходный смысл: блокировать собственное обещание бессмысленно. Вопрос Q17 предлагал выбор между пре-фандом и минтом при одобрении.

Ответ заказчика:

> «я буду пополнять пул призов из других проектов в ручную а проект будет только выдавать награду»

## Решение

**Модель: единый пул призов (`PrizePool`), который студия пополняет вручную и вне программы. Программа умеет только выдавать.**

1. Программа **не получает mint authority** ни над одним активом. Это главное следствие ответа, и оно сильнее, чем кажется: программа физически не может создать награду, которой не существует. Невозможно «напечатать» выплату — ни из-за бага, ни из-за скомпрометированного модератора.
2. `PrizePool` — PDA-токен-аккаунты (по одному на каждый fungible-mint) + PDA-владелец для NFT-минтов, которые студия заранее перевела в пул.
3. Пополнение — обычным SPL-переводом на адрес пула, **отдельная инструкция не нужна**. Это соответствует «пополнять вручную».
4. `payout` делает перевод из пула воркеру. Больше ничего.
5. `refund_expired` возвращает зарезервированное обратно в пул, а не создателю — при общем пуле это единственный непротиворечивый вариант.
6. Вывод средств из пула — отдельная инструкция `withdraw_from_pool`, доступная только admin/multisig, с rate limit за эпоху (требование раздела 3 промпта).

## Последствия

### Что это дало
- **Программа стала меньше и безопаснее**: нет CPI на mint, нет mint authority, нет риска неограниченной эмиссии. Меньше поверхность для аудита (Фаза 7).
- Ответственность за обеспечение наград — на студии и её казначействе, а не в коде. Это правильно: код не должен решать, есть ли у студии деньги.
- Пополнение вручную = студия контролирует расход физически, а не только программно.

### Новая проблема корректности, которую это создаёт — **решить до Фазы 2**

При общем пуле, тирах и M параллельных воркерах (ADR-0003 + ADR-0004) размер будущей выплаты **неизвестен до модерации**: модератор выбирает тир постфактум, и одобрить могут несколько сабмишенов одного задания. Значит при `create_task` нельзя зарезервировать точную сумму.

Варианты:
- (a) **Резервировать по худшему случаю**: `max_claims × amount_самого_дорогого_тира`. Программа отказывается открыть задание, если в пуле не хватает. Прозрачно и не может привести к невыплате, но заметно «замораживает» пул.
- (b) **Не резервировать**, проверять баланс только в `payout`. Пул расходуется экономно, но модератор может одобрить клип, а выплата упадёт с ошибкой нехватки. Для воркера это худший сценарий: работу приняли, награду не дали.
- (c) **Гибрид**: резерв по худшему случаю при `create_task` + явная проверка при `payout` + событие нехватки в backend, чтобы казначейство пополняло пул заранее.

**Рекомендация агента: (c).** Резерв защищает воркера от ситуации «одобрили, но не заплатили», а событие нехватки даёт операционный сигнал. Это требует поля `reserved_amount` на `TaskAccount` и инструкции `top_up`/`withdraw` с учётом резервов.

⚠️ Это единственное, что осталось решить по деньгам до написания кода.

### Прочее
- Награда в NFT требует, чтобы конкретный NFT **уже лежал в пуле**. Значит при `create_task` надо валидировать наличие предмета, иначе задание откроется с невыполнимой наградой.
- Нужен оффчейн-процесс: кто и как следит за балансом пула перед открытием заданий. Это операционная задача Фазы 3, не кода.
