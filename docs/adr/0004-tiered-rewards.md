# ADR-0004: Награды — тиры, присваиваемые при одобрении

- **Статус:** принято
- **Дата:** 2026-09-14
- **Решает:** Q6

## Контекст

Заказчик выбрал «тиры по сложности брифа» вместо фиксированной суммы. Это точнее отражает разброс качества клипов, но требует, чтобы выбор тира был частью инструкции `moderate`, а не задан заранее.

## Решение

1. Награда хранится на задании как набор тиров:
   ```rust
   pub const MAX_TIERS: usize = 4;

   #[derive(AnchorSerialize, AnchorDeserialize, Clone, Copy)]
   pub struct RewardTier {
       pub tier_id: u8,
       pub token_amount: u64,      // базовые единицы, decimals из mint
       pub token_mint: Pubkey,     // игровой токен студии — см. ADR-0002
       pub nft_reward_id: Option<Pubkey>,
   }

   // в TaskAccount:
   pub tier_count: u8,
   pub tiers: [RewardTier; MAX_TIERS],
   ```
2. **Размер `reward_amount` как единственное поле из промпта убирается.** Фиксированный массив вместо `Vec` — Anchor-аккаунт должен иметь детерминированный размер.
3. Инструкция `moderate` принимает `tier_id` как аргумент: модератор одобряет клип **на конкретном тире**. Программа валидирует `tier_id < tier_count`.
4. `payout` читает тир из одобренного сабмишена и переводит ровно то, что записано в тире.

## Последствия

- Порядок величин награды (вопрос Q6) остаётся открытым в части конкретных цифр — тиры объявляются при создании задания, поэтому числовые значения в код не зашиты. Это снимает блокер с Фазы 2.
- Юнит-экономика (раздел 8 промпта) считается по фактическому выданному тиру, а не по «средней награде». Нужно логировать `tier_id` в событии `payout` — иначе аналитика не соберётся.
- Модератор получает дискрецию в размере выплаты. Это риск произвольных решений → нужен аудит-лог модерации в backend и, желательно, второй модератор на дорогих тирах (см. Q11).
- Риск переполнения: `token_amount` в базовых единицах при `u64` переполняется при некорректных decimals. Проверка decimals mint'а при создании задания обязательна (см. раздел D промпта про SKR decimals=6 — та же ловушка).
