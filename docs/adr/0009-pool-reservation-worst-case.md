# ADR-0009: Резервирование пула по худшему случаю + сигнал нехватки

- **Статус:** принято (вариант (c) из ADR-0006 — по рекомендации агента, подтверждено заказчиком)
- **Дата:** 2026-09-14
- **Решает:** Q20

## Контекст

ADR-0006 ввёл единый пул призов, который студия пополняет вручную. Это породило проблему корректности: при общем пуле, тирах (ADR-0004) и M параллельных воркерах (ADR-0003) **размер будущей выплаты неизвестен до модерации** — тир выбирает модератор постфактум, а одобрить могут несколько сабмишенов одного задания. Точный резерв при `create_task` посчитать нельзя.

## Решение

Принят **гибридный вариант (c)**:

1. **Резерв по худшему случаю при `create_task`:**
   ```
   reserve = max_claims × max(tiers[*].token_amount)
   ```
   Если свободных средств в пуле (`available = balance − total_reserved`) не хватает — задание **не открывается**, инструкция падает с `Error::InsufficientPoolReserve`. Это защищает воркера: раз задание открыто, награда за него обеспечена.
2. **Повторная проверка в `payout`.** Резерв не заменяет проверку фактического баланса токена в пуле — пул мог быть опустошён вне программы (например, ошибочным выводом).
3. **Событие нехватки.** При нехватке эммитится `PoolShortfall { mint, required, available }`. Backend слушает его и уведомляет казначейство. Это операционный сигнал, а не аварийная остановка продукта.
4. **Учёт резервов в `PoolState.total_reserved`**, освобождение — при `refund_expired` и при закрытии задания.

## Последствия

- **Пул «замораживается» заметнее, чем расходуется.** При `max_claims = 5` и четырёх тирах резервируется 5 × самый дорогой тир, хотя выплачено будет существенно меньше. Для пилота это приемлемо и даже полезно: казначейство видит реальную нагрузку на пул заранее.
- **Модератор не может одобрить клип, если награда не обеспечена.** Это намеренно: сценарий «работу приняли, награду не дали» хуже, чем «задание не открылось».
- `withdraw_from_pool` обязан учитывать `total_reserved` — вывести можно только `available`. Иначе вывод ломает резервы открытых заданий.
- **Риск переполнения:** `max_claims × max_amount` в `u64` переполняется при больших значениях. Проверка `checked_mul` обязательна — это не стилистика, а защита от silently неверного резерва.
- Для NFT резерв считается иначе: конкретный предмет либо лежит в пуле, либо нет. Проверка наличия — при `create_task`, отдельная арифметика резерва не нужна.
