# ADR-0017: Backend модерации не подписывает решения

- **Дата:** 2026-09-15
- **Статус:** принят
- **Связано с:** ADR-0004 (тиры выбирает модератор), ADR-0006 (программа не держит mint authority), ADR-0011 (trust score), ADR-0012 (симуляция не платит)

## Проблема

`moderate` — единственная инструкция, пишущая `trust_score`, и единственный путь к
выплате из пула призов. Дашборд модерации — это интерфейс к ней, и он становится
самой привлекательной целью атаки: кто контролирует дашборд, тот решает, кому
уходят награды.

Наивная архитектура «backend держит ключ модератора и сам отправляет транзакции»
превращает компрометацию веб-сервера в прямую кражу из пула. Это ровно тот же
класс ошибки, от которого защищает ADR-0006 на уровне программы.

## Решение

**Backend не подписывает и не отправляет транзакции.** `POST /api/decisions`:

1. определяет подписанта,
2. сверяет его с `PoolState.moderatorAuthority`,
3. валидирует решение,
4. пишет аудит-лог,
5. возвращает описание инструкции `moderate` для подписи кошельком.

Ответ всегда содержит `"signed": false`. Ключа модератора на сервере нет — ни в
env, ни в файле.

Следствие: украденный backend даёт доступ к очереди на чтение и к подделке
аудит-лога, но **не даёт одобрить ни одной выплаты**. Ончейн-проверка
`signer == moderator_authority` остаётся единственным источником истины.

## Три решения, которые легко было сделать наоборот

### Authority читается с чейна, а не из конфига

`moderatorAuthority` приходит через `ChainSource.getPoolState()`. Хранить его в
env было бы проще и быстрее — но тогда безопасность программы сводилась бы к
безопасности конфига backend'а, а ротация модератора требовала бы деплоя
backend'а.

### Право проверяется раньше корректности решения

`authorizeDecision` сначала проверяет подписанта. Если проверять сначала
решение, неавторизованный вызывающий по кодам ошибок (`AlreadyDecided`,
`InvalidTierId`) сможет зондировать содержимое очереди. Это покрыто отдельным
тестом, потому что порядок проверок — неочевидная деталь, которую легко
«отрефакторить».

### Отказ без причины отклоняется

В модели конкурса (ADR-0003) отклонённые воркеры работали впустую. Отказ без
причины лишает их единственной обратной связи, и репутация площадки падает.
Проверка отклоняет и пустую строку, и строку из пробелов.

## Отклонено: держать ключ на сервере с HSM/multisig-обвязкой

Вариант рабочий в принципе (Squads + сервер как один из подписантов), но он
оставляет сервер в цепочке доверия. Для пилота на 10–20 воркеров подпись
кошельком в браузере модератора дешевле и безопаснее. Вернуться к этому стоит,
если ручная подпись станет узким местом — но это данные пилота, не догадка.

## Аутентификация: SIWS (добавлено тем же днём)

Первая версия брала подписанта из заголовка `x-moderator` без криптопроверки, и
это было помечено как главный пробел. Закрыто: вход выполняется по ed25519-подписи.

Сервер выдаёт одноразовый nonce, **привязывает его к заявленному адресу** и
возвращает готовый текст сообщения — клиент не собирает его сам, поэтому
расхождение формата между клиентом и сервером невозможно. При проверке сервер
восстанавливает адрес из подписи и только потом сверяет его с
`moderatorAuthority`.

Два решения, которые стоит зафиксировать:

- **Роль проверяется после криптографии.** Иначе, отвечая по-разному на верную и
  неверную подпись для разных адресов, можно перебором выяснить, какой адрес
  является модератором.
- **Неудачная проверка nonce не сжигает.** Отметка «использован» ставится только
  после успешной верификации, иначе злоумышленник сжигал бы nonce'и, угадывая их.

Реализация на `node:crypto` (ed25519), без `@solana/kit`: для проверки подписи
весь SDK не нужен. Подпись WebCrypto и `node:crypto` для ed25519 байт-в-байт
совпадает — проверено, поэтому браузерная подпись проверяется сервером напрямую.

Dev-режим с заголовком остался для отладки без кошелька, включается только через
`SIXSEC_AUTH=dev` и по умолчанию выключен.

## Что открыто

**В дашборде нет настоящего кошелька.** Вход подписывается демо-ключом, который
сервер создаёт при запуске и отдаёт на `/api/dev/demo-key` (только в mock-режиме;
вне него — 404, что покрыто тестом). Протокол при этом настоящий, подмена —
только источник ключа. Подключение Wallet Adapter'а — задача клиента (Фаза 4).

**Аудит-лог — JSONL на диске.** Для одного модератора достаточно. Для нескольких
нужен Postgres: конкурентная запись и поиск по истории. Осознанно отложено,
чтобы не тащить БД раньше реальной нагрузки.

## Проверка

37 юнит-тестов (`node:test`, без фреймворка) + `tsc --strict --noEmit`. Покрыто:
отказ чужому кошельку (403), регистрозависимость сравнения base58-адресов,
порядок проверок, несуществующий и отрицательный тир, граница длины причины,
повторное решение по уже решённому сабмишену, мусор в теле запроса (400),
`signed: false` в ответе, и потеря разрядов при сериализации u64 выше 2^53.

Последний тест заслуживает отдельного упоминания: первая его версия проверяла
`2^63` и **прошла бы впустую** — степень двойки точно представима в double, и
потеря разряда на ней не видна. Значение заменено на `2^63 + 1`. Ошибка была в
самом тесте, а не в коде, и нашлась только потому, что тест содержал контрольное
утверждение.
